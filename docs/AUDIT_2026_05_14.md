# v1.0 Pre-Tag Audit — 2026-05-14

**Auditor:** Independent senior Rust reviewer (agent under autonomy mandate)
**Scope:** All 9 crates under `crates/` (~32.5k LOC Rust), 24 spec docs,
3 example FSMs, 24-fixture conformance suite. Reviewed against `docs/00`
patch list and Doc 23 §9 MVP gates.
**Method:** `cargo {build,test,clippy,fmt}` (all clean, 413 tests pass),
static read of every critical-path file, grep-based cross-cuts, manual
walkthrough of the CLI on the three shipped examples (`fsm check` /
`generate --target c99` / `fmt --check` / `test`), then a hand-run gcc
build of the generated Motor sources.

---

## Executive Summary

**Verdict — not yet: P0 blockers (5).** The workspace builds, every test
listed in `cargo test` passes, clippy and rustfmt are clean, and the CLI
exercises the happy paths. But the AST→IR lowering in `fsm-analyzer`
silently **drops every user-authored guard, transition action,
entry/exit action, and payload binding**. That defect cascades through
the simulator and the C codegen: traces "pass" because the simulator
doesn't execute the dropped actions, the gcc test compiles because the
generated C never references the dropped statements, and the conformance
suite passes because its expected-output files only assert symbol
presence. Three additional P0 issues compound the picture: parallel
state machines emit unused `_state_region_N` slots that no codegen ever
writes (parallel codegen is therefore non-functional end-to-end); timer
transitions in the IR carry no distinguishing trigger and lower to the
universal `EVENT__COMPLETION` (so any `after X ms` collides with `done`
transitions); the table dispatch strategy is documented as B-11
collect-then-execute but in practice walks `m->_state` exactly like the
switch strategy. **Do not tag v1.0 in this state.** Fix the five P0
items, add three or four loop-closing tests, and the workspace is
re-tag-ready.

## Findings

### P0 — Blockers (must fix before tag)

#### P0-1 — AST→IR lowering drops every user guard, action, payload binding, and entry/exit body

**File:** `crates/fsm-analyzer/src/lower.rs`

**Cite:**

- `build_transition` (L1023–1049): `guard: None`, `actions: Vec::new()` —
  unconditional, no use of `t.guard()` / `t.actions()`.
- `lower_external` (L931–955), `lower_internal` (L957–979),
  `lower_local` (L981–1000), `lower_completion` (L1002–1021): none call
  `.guard()` or `.actions()` on the parsed transition.
- `lower_external` etc.: `Trigger::Event { payload_binding: None, .. }`
  is set unconditionally — payload-name binding (`FAULT(code)`) is
  discarded.
- `lower_state` (L670–679): `entry`/`exit` body collapsed to
  `Vec::new()` via `.map(|_ab| Vec::new())`.
- `lower_timers` (L1051–1098): `actions: Vec::new()` for every timer.

**What this means.** The DSL example shipped at
`examples/motor/motor.fsm` declares
`on START [can_start] -> Running : ctx.count = ctx.count + 1; set_speed(100)`.
After analysis the IR contains a transition with `guard = None` and
`actions = []`. The simulator's `execute_statements(&t.actions, ...)`
runs over an empty slice. The codegen's per-case emit
(`crate::stmt::emit_stmts(&t.actions, …)` in
`dispatch_switch.rs` L167) produces no source lines. The dispatch is
just `Motor_exit_IDLE(m); m->_state = MOTOR_STATE_RUNNING; Motor_entry_RUNNING(m);`
— guard not consulted, counter not incremented, `set_speed(100)`
unreferenced. Manually verified by running
`cargo run -p fsm-cli -- generate --target c99 --out /tmp/m examples/motor/motor.fsm`
and grepping the output: `can_start`, `set_speed`, `count`,
`last_fault_code`, `reset_link` appear **only** in struct declarations.
The MVP language is non-functional.

**The golden_end_to_end test acknowledges the gap.**
`crates/fsm-cli/tests/golden_end_to_end.rs` L211–215:
*"The analyzer's v1.0 lowering does not yet emit guard expressions on
transitions, so the `[can_start]` annotation in motor.fsm has no effect
…"* The conformance fixtures (`expected/Motor.c.contains`) only assert
public-API symbol presence; they cannot detect this drop.

**Fix.** Implement guard / action / payload-binding lowering. Concretely
the analyzer should:

1. Call `t.guard()` on each AST transition and lower the contained
   `Expr` to `GuardExpr` (mirror the determinism check's `GuardShape`
   extraction in `checks/determinism.rs`, but produce IR `GuardExpr`
   nodes per `crates/fsm-ir/src/model.rs`).
2. Call `t.actions()` and lower each `Stmt` into `fsm_ir::Statement`.
3. Lift the entry/exit `ActionBlock` into IR `Statement` vectors at
   `lower_state` L670–679.
4. Capture payload binding for `Trigger::Event` when the AST trigger
   has an `Ident` parameter list.

Add an integration test that emits Motor.c and asserts the strings
`can_start`, `set_speed(100)`, `m->context.count = m->context.count + 1`,
and `reset_link()` appear.

#### P0-2 — Parallel state machines: per-region state slots are declared and read but never written

**Files:**

- `crates/fsm-codegen-c/src/emit/header.rs` L211–218 (declares
  `_state_region_N` per parallel region)
- `crates/fsm-codegen-c/src/emit/completion.rs` L172–183 (reads
  `m->_state_region_N`)
- `crates/fsm-codegen-c/src/emit/source.rs` L82–124 (`emit_init`: only
  writes `m->_state`, ignores `_state_region_N`)
- `crates/fsm-codegen-c/src/emit/dispatch_switch.rs` L173 & L196–217
  (dispatch reads/writes `m->_state` only)
- `crates/fsm-codegen-c/src/emit/dispatch_table.rs` L177, L260, L295
  (same)

**What this means.** `grep -rn "_state_region" crates/fsm-codegen-c/src`
returns exactly **two** sites: the header *declaration* and the
completion-helper *read*. No emitter ever assigns into
`m->_state_region_N`. Yet B-08's all-regions-final check in
`emit_all_regions_final_helper` synthesizes
`m->_state_region_0 == MOTOR_STATE_AFINAL` clauses that, in practice,
compare zero-initialized memory against final-state IDs. Parallel
completion detection therefore relies on dead variables. Worse, the
single `m->_state` slot can only encode one active leaf — a parallel
machine with two regions has no place to record the second active leaf
at all.

The conformance test `crates/fsm-codegen-c/tests/parallel_completion.rs`
only asserts the *names* of these symbols appear in the generated text
(`c.contains("_state_region_0")` etc.). No test compiles and runs a
parallel-state binary, so the gap is invisible at the cargo level.

**Fix.** Decide on a representation for multi-active-leaf state. Two
viable options:

1. **Active-leaf array.** Replace `m->_state` with a fixed array
   `m->_active[MAX_PARALLEL_REGIONS]` where slot 0 is the single-region
   leaf and slots 1..N are the per-region leaves. Update init,
   dispatch, and entry/exit emitters to thread the active-region index
   through the transition selection.
2. **Region slots used.** Keep `_state` for the single-region path,
   wire `_state_region_N` writes through the entry/exit emitters when
   the leaf lives inside a parallel region, and have the dispatch
   iterate over the parallel region slot vector (B-11 collect-then-
   execute, which is also missing — see P0-3).

Either way the gcc test must grow a parallel fixture and assert the
end-to-end transition.

#### P0-3 — Table-dispatch strategy is not B-11 collect-then-execute

**File:** `crates/fsm-codegen-c/src/emit/dispatch_table.rs`

**Cite:**

- L287–308: the emitted `Motor_dispatch` body reads `m->_state` once,
  walks the parent table, returns on the first hit — identical
  structure to the switch strategy in
  `dispatch_switch.rs` L194–222.
- Doc 00 §7.8 / B-11 mandates a **per-region collect phase** producing
  a `selected[MOTOR_MAX_PARALLEL_REGIONS]` buffer, then an execute pass
  iterating that buffer.

**What this means.** The crate-level docstring (L1–5) and the inline
comment at L290–291 advertise "B-11 collect-then-execute," but the
generated dispatcher never iterates regions, never builds a
`selected[]` buffer, and returns on the first match — exactly the
early-return bug B-11 was written to fix. For a non-parallel machine
this is harmless because the switch and table strategies happen to
produce the same outer loop. For a parallel machine the table
strategy is no more correct than the switch strategy (and given P0-2
neither is correct).

A secondary defect in the table strategy worth surfacing: each row
emits `guard_idx: 0, action_idx: 0` as placeholders
(`dispatch_table.rs` L143–144) and the executor function at L163–184
is dead — execution happens in the
`{prefix}_try_apply_row` inline switch (L218–284) using
`find_transition_at_pos` (L312–362), which matches by
`(source, trigger, priority)`. Two transitions with the same triple on
the same source state will collide; the analyzer rejects unguarded
duplicates but two transitions distinguished by `[else]` versus
`[guard_expr]` share priority 0 and a trigger, so the
position-recovery would mis-route.

**Fix.** Re-implement `dispatch_table::emit_outer_dispatch` to emit
the normative algorithm from Doc 00 §7.8:

```c
const Motor_TransRow_t *selected[MOTOR_MAX_PARALLEL_REGIONS];
uint8_t selected_count = 0;
for (uint8_t r = 0; r < Motor_active_region_count(m); r++) {
    Motor_StateId_t s = Motor_active_leaf_of_region(m, r);
    ...                       /* ancestor walk per region */
    if (best) selected[selected_count++] = best;
}
for (uint8_t i = 0; i < selected_count; i++) Motor_execute_transition(...);
```

The `Motor_execute_transition` stub at L163–184 also has to gain a
real body (it currently just sets `m->_state = row->target`, skipping
exit/entry/action sequencing).

Also drop the `find_transition_at_pos` fragile-matching path and have
`collect_transitions` produce stable indices by emitting a
deterministic per-row payload at codegen time.

#### P0-4 — Timer triggers indistinguishable from completion events; timers never armed on entry

**Files:**

- `crates/fsm-codegen-c/src/emit/dispatch_switch.rs` L128–135 (After /
  Every / EveryInternal → `EVENT__COMPLETION`)
- `crates/fsm-codegen-c/src/emit/timer.rs` L106–115 (timer fires
  `EVENT__COMPLETION`)
- `crates/fsm-codegen-c/src/emit/source.rs` L113–122 (`Motor_init`
  arms timers only for the initial leaf)
- `crates/fsm-analyzer/src/lower.rs`: `Trigger::After` / `Trigger::Every`
  are never produced — every timer-driven transition has `trigger:
  None` after lowering and ends up indistinguishable from a `done`
  completion.

**What this means.** In `motor.fsm`,
`state Running { after 5000 ms -> Faulted; on STOP -> Idle; ... }`. The
generated C arms `_timer_RUNNING_M_Motor_timer_after_remaining_ms` only
inside `Motor_init` — but the initial state is `Idle`, so the slot is
zero. When `dispatch(START)` enters `Running`, no code writes the
timer slot. `Motor_advance_clock` then guards on `remaining_ms > 0`
and silently does nothing for the lifetime of the program. Even if it
did arm, the timer fires `MOTOR_EVENT__COMPLETION`, which is the same
event the `done` transition uses. A machine that mixes `after` and
`done` in the same state has undefined dispatch behaviour.

`Trigger::After` / `Trigger::Every` exist in the IR enum but the
analyzer never constructs them — every `after X ms` becomes a
zero-trigger transition under timer ownership, which both codegen
back-ends (switch + table) treat as a completion catch-all.

**Fix.**

1. Lower `after`/`every` timer declarations into either dedicated
   `Trigger::After { timer_id }` / `Trigger::Every { timer_id }` IR
   triggers OR into synthetic timer-event IR events with stable IDs;
   propagate the timer id through codegen so each timer fires its own
   enum value.
2. Arm timer slots on every entry into the timer-owning state, not
   just at `Motor_init`. The natural seam is the `entry_path` emit in
   `dispatch_switch::emit_one_case` and the `walk_initial` chain in
   `Motor_init`.
3. Update `Motor_advance_clock` to fire the timer's own event id.

#### P0-5 — `defer EVENT` is documented as "store and return" but actually drops the event

**Files:**

- `crates/fsm-codegen-c/src/emit/dispatch_switch.rs` L201–206
- `crates/fsm-codegen-c/src/emit/dispatch_table.rs` L292–294

**Cite (switch dispatcher):**

```c
if (ev->id < EVENT__COUNT && (defer_mask[m->_state] & (1u << ev->id))) {
    /* Deferred — store and return without processing. v1.0 simplifies
     * the defer queue to a single slot per state; multi-slot defer is
     * tracked under follow-up work. */
    return;
}
```

The comment promises a single-slot store but the code is a bare
`return`. The generated machine struct has no defer slot. The event is
not stored, not re-played, not raised. `defer EVENT` becomes "drop
EVENT silently while in this state," which is the opposite of UML
defer semantics and violates Doc 02 G1 (no undefined behaviour) — the
user reads a documented behaviour that the implementation contradicts.

**Fix.** Either (a) ship a real defer queue (separate ring buffer or
flag bit re-injection on state change) and update the comment to match
behaviour, or (b) emit `FSM-E0903` ("defer queue capacity exceeded")
at codegen time on every `defer EVENT` and remove the
silent-drop path until v1.1. Option (b) is the cheaper way to keep G1.

### P1 — High (fix soon, but won't block tag if scope is explicit)

#### P1-1 — `cargo test` trace-mode comparison treats empty `expected` as success

**File:** `crates/fsm-simulator/src/trace.rs` L237–252.

```rust
if !trace.expected.is_empty() {
    /* compare actual vs expected */

...
matches_expected: trace.expected.is_empty() || first_mismatch.is_none(),
```

#### P1-2 — G7 coverage map admits 39 / 75 diagnostic codes are UNTESTED

**File:** `tests/conformance/COVERAGE_MAP.md`.

Summary table: `Tested 36 / UNTESTED 39 / Total 75`. Doc 23 §9 G7
requires ≥ 1 test per diagnostic code. Untested codes include
foundational ones: `FSM-E0005`, `FSM-E0006`, `FSM-E0011`, `FSM-E0012`,
`FSM-E0025`, `FSM-E0105`, `FSM-E0110`, `FSM-E0202`, `FSM-E0203`,

#### P1-3 — gcc test is the only end-to-end gate and only exercises the in-memory Motor fixture

**Files:** `crates/fsm-codegen-c/tests/gcc_compile.rs`,
`crates/fsm-cli/tests/golden_end_to_end.rs`.

Both tests use `common::motor_ir()` / `tests/fixtures/motor.fsm` and
write user-stub entry/exit/extern bodies. **Neither runs the three
shipped examples through the generate-then-gcc pipeline.** G4
("`gcc -std=c99 -Wall -Wextra -Wpedantic -Werror Motor.c` exit 0") and
G6 ("3 examples through full chain + simulator-trace-match") are
therefore not back-stopped against the canonical `examples/`. Both
tests silently `return` when gcc is missing on PATH (L101–104), so a
CI runner without gcc reports green while skipping the gate entirely.

Fix: emit + gcc-compile + run the three example FSMs in a single new
integration test, and have it `panic!` rather than skip when gcc is
unavailable (or gate on a clearly-named environment variable, never
the absence of the tool).

#### P1-4 — Import path security ends at shape check; workspace-root canonicalisation never happens

**File:** `crates/fsm-parser/src/import_resolver.rs` L1–66.

The module docstring (L8–9) explicitly says
*"the workspace-relative canonicalisation step is the resolver's
responsibility downstream"* but `grep -r canonicalize crates/`
returns zero hits. There is no downstream resolver. Doc 00 §7.12
requires `Path::canonicalize` plus a workspace-root containment check
("assert the result starts with the workspace root"). Today an attacker
controlling a `.fsm` file can craft `import "valid/../valid_lookalike.fsm"`
— the `..` segment is correctly rejected, but `import "valid/symlink"`
where `symlink` points outside the workspace is not detected because
no follow-symlinks resolution happens. The shape check is necessary
but not sufficient.

Fix: implement the canonicalize-plus-prefix check as `resolve_import`
inside `fsm-parser` (or `fsm-cli`'s loader) and call it before any
imported `.fsm` is opened.

#### P1-5 — No parser DoS limits (input size, recursion depth, token count)

**File:** `crates/fsm-parser/src/parse.rs` and `crates/fsm-parser/src/parser.rs`.

`grep -rn 'max_depth\|MAX_DEPTH\|recursion_limit\|MAX_INPUT' crates/fsm-parser/` returns nothing.
The recursive-descent parser is exposed via `parse(src: &str)` with no
caps, so a deeply nested expression file (`((((((... 100 000 levels)))))) ;`)
or a multi-gigabyte input will exhaust stack / RAM. Doc 00 §7.12 G-02
folds parser hardening into the security gate.

Fix: enforce an explicit limit (e.g. 1 MiB input, depth 256) at the
top of `parse()` and abort with `FSM-E0010` plus a clear message.

#### P1-6 — `Motor_init` writes `_state` twice and never sets parallel-region slots

**File:** `crates/fsm-codegen-c/src/emit/source.rs` L82–124.

`emit_init` always emits
`m->_state = MOTOR_STATE_ROOT;`
immediately followed by
`m->_state = MOTOR_STATE_IDLE;`
(generated source confirmed at `/tmp/fsm_audit_motor/Motor.c`).
Cosmetic, but indicative — the initial-state computation runs after a
`memset(0)` plus an unnecessary write. Fix: emit a single, definitive
write to the resolved initial leaf.

The bigger issue is the missing parallel-region slot init — see P0-2.

#### P1-7 — Simulator silently downgrades guard-eval errors to `false`

**File:** `crates/fsm-simulator/src/interpreter.rs` L665, L586, L1048.

```rust
if !eval_guard(g, &evctx).unwrap_or(false) { continue; }
```

A runtime-undefined guard (e.g. arithmetic overflow, divide-by-zero in
a guard expression) silently disables the transition rather than
surfacing the error. A real conformance test cannot tell "the guard
returned false" from "the guard errored." Replace with explicit
`Err(e) => return Err(StepError::GuardEval(e))` and add a regression
test for E0207-style guards.

#### P1-8 — `panic!` and `expect()` paths inside the codegen invariant boundary

**File:** `crates/fsm-codegen-c/src/state_index.rs` L111–118 (`must_lookup`).

If the analyzer ever fails to reject an unindexed state id (e.g.
incomplete lowering, future schema field), `fsm generate` aborts the
process with a `panic!`. The CLI should `Result`-propagate so users
get exit code 2 and a diagnostic, not a process abort and stderr
backtrace. Same pattern for the lexer's `unreachable!("lex_newline …")`
at `crates/fsm-lexer/src/lexer.rs` L177 — currently safe by construction,
but the test path at L864 prints `expected E0004, got {other:?}` then
panics in test code, which is fine; non-test panic! at L111 is the
real bite.

#### P1-9 — README advertises features that Doc 00 explicitly deferred

**File:** `README.md`.

L11–13 list "Simulator — WebSocket-based, virtual clock, deterministic
replay" and "VS Code extension — syntax highlighting, LSP, live diagram
panel, simulator panel" and "Web IDE." Doc 00 §6 D-01..D-04 / B-02 /
B-04 defer all three to v1.1+. Either remove the bullets or add an
"v1.0 ships:" sub-list that names only the in-scope components
(parser, analyzer, codegen-c, formatter, in-process simulator, CLI).

### P2 — Medium (post-1.0 cleanup)

#### P2-1 — Conformance fixtures check only that symbols *appear*, not that machines *behave*

**Files:** `tests/conformance/codegen-c/00*/expected/*.contains`.

The `Motor.c.contains` file lists three identifiers (`Motor_init`,
`Motor_dispatch`, `Motor_current_state`). Tests pass when those
substrings appear anywhere in the file, even if the dispatch is empty.
Replace with byte-exact golden masters or with a downstream gcc-link
step.

#### P2-2 — Codegen-c hard-caps machine size at 255 states

**File:** `crates/fsm-codegen-c/src/state_index.rs` L176–179.

`u8::try_from(self.records.len()).expect("…")` panics if a machine
exceeds 255 states. For an embedded-target codegen, 255 is usually
plenty, but the `expect` should be an error returned through `Result`
so `fsm generate` exits non-zero rather than aborting.

#### P2-3 — Table dispatch's `(source << 8) | trigger` switch can collide on wide enums

**File:** `crates/fsm-codegen-c/src/emit/dispatch_table.rs` L222–229.

The case label `(STATE << 8) | trigger` assumes both fit in 8 bits.
With 256 events or 256 states the values alias. Generated C currently
compiles (because each test machine is small), but the synthetic key
should encode width explicitly (`uint32_t`) and guard against
overflow at codegen time.

#### P2-4 — `c.id`/`p.id` parent-find loops use `find_parallel`/`find_initial_target` linear walks

**Files:** `crates/fsm-codegen-c/src/emit/completion.rs` L200–227;
`crates/fsm-codegen-c/src/emit/source.rs` L169–198.

Each emit pass re-walks the IR tree to look up a parallel state by id.
Performance is fine for v1.0, but the analyzer's `MachineIndex`
already maintains the lookup map; either share it through `MachineEmitCtx`
or precompute the index alongside `StateIndex`.

#### P2-5 — Magic `1024` loop guards in the simulator

**Files:** `crates/fsm-simulator/src/interpreter.rs` L705–706, L729–730, L1247–1248.

Three open-coded `while guard < 1024` ancestor walks. Replace with a
named constant (e.g. `MAX_STATE_DEPTH = 256`) so the limit is
discoverable and adjustable.

#### P2-6 — Timer field names embed the stable-id metadata

**File:** `crates/fsm-codegen-c/src/emit/source.rs` L222–248 and
`crates/fsm-codegen-c/src/emit/timer.rs` L34–46.

Generated C field `_timer_RUNNING_M_Motor_timer_after_remaining_ms`
is unnecessarily long — the `M_Motor_timer_after` segment is the
internal stable id. Trim to `_timer_running_after_remaining_ms` or
similar before emission.

#### P2-7 — Two distinct `MachineIndex` types — duplicated parent map

**Files:**
- `crates/fsm-analyzer/src/lca.rs::MachineIndex`
- `crates/fsm-simulator/src/runtime/machine_index.rs::NodeRef`

Both build a state → parent map by walking the IR. The simulator's
version is richer (regions, transitions, timers), but the LCA
parent-walk is duplicated. Consider exposing the analyzer's index as
the canonical foundation and having the simulator extend it.

#### P2-8 — `expect`/`unwrap` count in production code (87 sites)

`grep -rn '\.unwrap()' --include='*.rs' | grep -v 'tests/'` returns 87
hits. Many are infallible after analyzer validation, but the count
should be triaged: anything reachable from a public API entry
(`parse`, `analyze`, `emit`, simulator step) should `Result`-propagate.

#### P2-9 — Defer codegen `uint32_t` mask hard-caps event count

**File:** `crates/fsm-codegen-c/src/emit/defer.rs`.

Only the first 32 events can be deferred. Fine for embedded reality
but should be documented; today only the source comment mentions it.
For machines exceeding 32 events the emitter should reject (or widen
to `uint64_t` plus a multi-word mask).

#### P2-10 — Doc 00 patch list has nothing crossed off

**File:** `docs/00-Decisions-And-Reconciliation.md` §8.

The doc-update plan lists every per-spec patch ("Doc 02 §13 DELETE
tables," "Doc 11 §8 rewrite per B-10," etc.). None of the 24
specifications has been touched on disk relative to the `b-08`
references in the implementation. A pre-1.0 tag should either apply
the patches or explicitly mark Doc 00 as the authoritative source for
v1.0 and the older docs as "informative — see Doc 00."

#### P2-11 — `cargo build` finishes in 2.8 s on warm cache, but `dispatch_table.rs` emits Quadratic O(N×N) text

`find_transition_at_pos` (`dispatch_table.rs` L312–362) re-walks the
entire IR tree for each emitted row. With N transitions this is
O(N×N) at codegen time. Fine today, will hurt on real industrial
machines. Replace with a pre-built index.

#### P2-12 — `Trigger::After` and `Trigger::Every` are dead IR variants

The IR enum has the variants (`crates/fsm-ir/src/model.rs`) but no
producer ever constructs them — the analyzer always emits `trigger:
None` for timer transitions. Either wire them up (paired with P0-4)
or delete the variants and rely on a synthetic timer event.

### P3 — Low (nits, tracking-only)

#### P3-1 — `dispatch_switch.rs` L116 `let _ = macro_prefix;` and similar dead-let suppressions

Several emit modules end with `let _ = …;` to silence unused-variable
warnings; the warnings would not appear if the unused binding were
just not introduced. Minor noise.

#### P3-2 — `state_index.rs` L273 `const _: Option<StateRecordKind> = None;` workaround

A "workaround keep import live" comment masks an actual unused
import. Remove the import and the workaround.

#### P3-3 — `header.rs` `emit_payload_structs` (L95–123): only `Type::Primitive` resolved; everything else falls through to `int`

For complex payload types (`enum`, `opaque`, `array`) the codegen
silently emits `int`. Currently unreachable because the analyzer
rejects non-primitive payloads, but the fallback should be a
diagnostic, not a silent type-narrowing.

#### P3-4 — Comment doctrine: WHY-only is respected, but several modules narrate

Examples: `crates/fsm-simulator/src/runtime/completion.rs` L9–17
explain "what" instead of "why." Per the cross-project comment
doctrine (TS/Py/Bash WHY-only; Rust is not formally pinned but the
codebase otherwise follows it), tighten.

#### P3-5 — `cargo clippy --pedantic` reports 80+ `#[must_use]` and `module_name_repetitions` warnings

Not a blocker (default-clippy is clean), but the pedantic noise
suggests no opinion has been formed on public-API hygiene.

#### P3-6 — `Motor_handle_completion` calls `Motor_all_regions_final` on every entry even for
machines with no parallel states

`emit_handle_completion` adds `(void)Motor_all_regions_final;` (L31–34)
to silence -Wunused-function, then `Motor_all_regions_final` itself is
emitted as an empty `return false;` shell. Net cost is one
unreachable function symbol per machine — fine, but reads as cruft.

#### P3-7 — `Motor_handle_completion` watchdog increments `m->_completion_depth` and asserts ≤ 64

This is per-machine, but the analyzer has no equivalent compile-time
check on completion chain depth. A pathological IR could blow the
runtime assertion at first use. Either lift to analyzer time or
document the runtime invariant in the public API.

## Categorical observations

### Correctness

The 14 BLOCKERS from `VALIDATION_REPORT.md` and the §10 TL decisions
in Doc 00 are partly addressed: the analyzer rejects `after 0 ms`
(B-13, `checks/timer.rs`) and history without `default ->` (B-14,
`checks/history.rs`); the analyzer's `MachineIndex` and the
simulator's `effective_lca` correctly implement B-09 (LCA-for-self);
B-08 parallel completion in the simulator (`runtime/completion.rs`)
correctly walks all regions before enqueueing.

But three blockers are only nominally fixed in the C codegen:

- **B-08 (parallel completion in codegen-c):** helper emitted, but
  parallel state slots are dead (P0-2).
- **B-10 (switch ancestor walk):** correctly emitted in
  `dispatch_switch.rs` — this one is solid.
- **B-11 (table collect-then-execute):** advertised in comments,
  missing in code (P0-3).

The most consequential gap is *not* a B-numbered blocker: it's the
silent drop of guard / action / payload-binding / entry-exit data
during AST → IR lowering (P0-1). Doc 00 doesn't flag it because it's
not a spec ambiguity; it's an implementation omission that the
golden_end_to_end test L211–215 explicitly acknowledges with a
"yet to ship" comment.

## Tagging recommendation

**Defer the v1.0 tag.** Five P0 issues materially break the value
proposition the README and Doc 00 promise — the most damaging is the
silent drop of guards and actions during lowering, which makes every
shipped example a no-op machine. The fix is local
(`crates/fsm-analyzer/src/lower.rs`), well-bounded (≈ 150-300 LOC of
guard/statement lowering paired with payload binding capture), and
testable end-to-end via the existing golden_end_to_end harness once a
"contains `set_speed(100)`" assertion is added. Parallel state slot
wiring (P0-2), B-11 collect-then-execute (P0-3), timer-trigger
identity (P0-4), and defer behaviour (P0-5) are the next four fixes.

After P0s are landed plus four targeted P1 fixes (P1-1 empty-expected
traces, P1-2 / P1-3 G7 / G4 coverage, P1-4 import canonicalize), the
workspace is tag-ready. The P2/P3 backlog can ship in v1.0.1.
