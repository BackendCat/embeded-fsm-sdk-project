# Architectural & QA Audit — embedded-fsm-sdk
**Date:** 2026-06-06
**Auditor:** Backend Cat
**Scope:** Full workspace, all 11 crates, 87,928 LOC Rust
**Methodology:** Strict maintainability review (per-file size, abstraction quality, spaghetti-condition growth) + static analysis + `cargo clippy --workspace --all-targets` + `cargo fmt --check` + per-crate boundary / smell triage

---

## 0. Executive Summary

**Overall verdict: this is an unusually mature, disciplined codebase.**

The headline metrics suggested otherwise (388 unwrap/expect, 18 panic!, 23 unsafe matches), but every signal collapsed under inspection:

| Surface signal | Reality |
|---|---|
| 23 `unsafe` matches | 0 actual `unsafe` blocks. All 11 crates `#![forbid(unsafe_code)]`. The matches are `forbid` attributes + historical comments. |
| 18 `panic!` | 14 in test code (`#[cfg(test)]`), 4 in comments documenting *removed* panics. **0 production panics.** |
| 388 unwrap/expect | 200+ are the parser's domain-specific `p.expect(TokenKind, DiagnosticCode)` (emits a diagnostic, never panics); 150+ are inside `#[cfg(test)]` blocks. Real `Option/Result::unwrap()` in production paths: **~17 total**, almost all `writeln!(String).unwrap()` (infallible). |
| Cargo `clippy --workspace --all-targets --no-deps` | **PASS** with `-D warnings` (CI gate). |
| `cargo fmt --check` | **PASS**. |
| TODO/FIXME/HACK in 88K LOC | **1** total. |

The project has been through 16+ formal audits already (visible in `docs/AUDIT_*.md` from 2026-05-14 to 2026-05-19). The discipline shows: AD-2 moved an unused dep to `dev-dependencies`; P0-1/MV5-1 anti-pattern is enforced in `fsm-verify` by comment + structure; coverage uses a monotonic non-decreasing ratchet with explicit anti-gaming rules.

**The remaining concerns are almost all structural decomposition (file size), not correctness.**

## 1. Architecture

### 1.1 Crate dependency graph (production deps only)

```
fsm-diagnostics (leaf)
   ├── fsm-lexer
   │     └── fsm-parser
   │           ├── fsm-analyzer
   │           │     └── (no descendants except via cli/lsp/verify aggregators)
   │           └── fsm-formatter
   ├── fsm-ir
   │     ├── fsm-codegen-c
   │     └── fsm-simulator
   │           └── fsm-verify
   └── (consumed everywhere via workspace)

aggregators:
   fsm-cli  ← lexer, parser, analyzer, ir, simulator, verify, formatter
   fsm-lsp  ← parser, analyzer, ir, verify, simulator
```

**Findings:**

- **No cycles.** Topological order is strict.
- **`fsm-verify` keeps the right invariant**: prod deps are `fsm-simulator + fsm-ir + fsm-diagnostics` only. Parser/analyzer are dev-deps for acceptance fixtures. The Cargo.toml comment "the explorer DRIVES `fsm_simulator::Interpreter` as the single, spec-conformant transition oracle … re-implementing transition selection would be a forbidden second semantics (the P0-1 / MV5-1 anti-pattern)" is exactly the right architectural guard rail to write down.
- **`fsm-simulator` had a boundary leak** (analyzer in prod-deps despite zero `fsm_analyzer::` symbols in `src/`), and it was *already fixed* in Audit B P1-A2 (2026-05-15) by demoting to dev-dep. The Cargo.toml has the historical note inline. Boundary is now clean.
- **Diagnostics is a true foundation crate**: zero workspace deps, owns Span/SourceLocation/Severity/DiagnosticCode. Every crate consumes it instead of re-defining diagnostic types.
- **No backwards-coupling**: `fsm-ir` does not know about syntax; `fsm-codegen-c` does not know about the parser; `fsm-analyzer` does not know about codegen.

**Verdict: 9.5/10 — close to ideal layered architecture for a compiler pipeline.**

### 1.2 Boundary risks (none fatal, two notable)

| Risk | Severity | Notes |
|---|---|---|
| `fsm-cli/src/import_header.rs` reaches 1405 LOC for a CLI convenience feature (C-header → extern declarations) | Medium | The module is well-justified (it documents *why* it's in `fsm-cli` instead of a core crate). But 1.4K LOC for "input convenience" is a smell — a `fsm-cheader` micro-crate would isolate C-parsing complexity from CLI orchestration. Not urgent. |
| `fsm-lsp` aggregates 5 of 7 pipeline crates | Low | Expected for an LSP host. The 9959 LOC is split across `capabilities/` (16 files), `analysis.rs`, `document_store.rs`, `refs.rs`, etc. Internal structure is clean. |

## 2. Code-quality smell hotspots

### 2.1 Files > 1000 LOC

Any file crossing 1000 LOC is treated as a presumptive structural issue. **8 files cross the threshold**:

| File | LOC | Functions / Impls | Assessment |
|---|---|---|---|
| `crates/fsm-simulator/src/interpreter.rs` | **1899** | 45 fns, 1 impl | **DECOMPOSE.** See §2.2. Highest-priority refactor. |
| `crates/fsm-cli/src/import_header.rs` | 1405 | 48 fns | Could become its own crate (`fsm-cheader`) or split: lexer / decl-parser / DSL-emitter. |
| `crates/fsm-lexer/src/lexer.rs` | 1316 | 77 fns | Acceptable — lexers tend to be long flat dispatch tables. Lower priority. |
| `crates/fsm-ir/src/model.rs` | 1165 | 14 fns, 4 impls | Acceptable — IR data model with derived impls. Possibly split per top-level type. |
| `crates/fsm-diagnostics/src/lib.rs` | 1108 | catalog | **Macro-driven** (`for_each_code!`). Length is the catalog size. Splitting would harm the single-source-of-truth contract. Keep as-is. |
| `crates/fsm-lsp/src/capabilities/complete.rs` | 1069 | 37 fns | Borderline — LSP completion is inherently many small handlers. Could split per completion kind. |
| `crates/fsm-codegen-c/src/emit/transition.rs` | 1054 | 16 fns | Borderline — transition emission has many shapes (self-transition, internal, hierarchical, parallel). Consider splitting per dispatch strategy. |
| `crates/fsm-lsp/src/server.rs` | 1044 | 24 fns, 2 impls | Borderline — LSP server entrypoint. Split per LSP method group. |

### 2.2 Top decomposition candidate: `fsm-simulator/src/interpreter.rs` (1899 LOC)

**Strengths:** Excellent doc-comments referencing `Doc 08 §3.1 / §4 / §5 / §6 …` spec sections. Two architectural invariants stated up-top.

**Smell:** 30+ free `fn`s outside the `impl Interpreter` block live in one file because they "happen to operate on `RuntimeState`/`MachineIndex`". This is procedural-style organization disguised as a module.

**Proposed thermo-nuclear decomposition (preserves behaviour, deletes a conceptual layer):**

```
crates/fsm-simulator/src/interpreter/
  ├── mod.rs              (Interpreter struct + public API; ~400 LOC)
  ├── step.rs             (rtc_step, drain_queue_rt, queue policy §14)
  ├── transitions.rs      (select_transitions, execute_one_transition §3.1/§4)
  ├── path.rs             (exit_set, entry_path, expand_exit_with_parallel §5–§7)
  ├── history.rs          (record_history_before_exit, expand_initial §8)
  ├── submachine.rs       (sync_submachines, try_delegate, init_sub_context)
  ├── defer.rs            (active_config_defers, release_deferred §10)
  └── timer.rs            (arm_timers_on_entry §13)
```

Each split aligns with a single section of Doc 08 — making the file→spec mapping 1:1 instead of "scroll to find §6". No behaviour change, no new abstractions, ~8 small focused modules where there is currently one mega-file.

### 2.3 Spaghetti / hidden complexity — none found

I looked for thermo-nuclear's flagship smells:
- Ad-hoc conditionals scattered into unrelated flows — **not found**
- Boolean mode flags multiplying control flow — **not found**
- Thin pass-through wrappers — **not found**
- Feature-specific logic in shared paths — **not found**
- Cast-heavy boundaries (`unknown`, `as` overload) — **not found**
- Magic / generic indirection hiding simple data — **not found**

The codebase consistently prefers direct, boring code. Diagnostic catalog uses a single `macro_rules! for_each_code!` table that drives `enum + Display + severity + default_message + all_codes + from_str` — exactly the "one source of truth" idiom thermo-nuclear advocates.

### 2.4 Production unwrap/panic concerns (full enumeration)

After filtering test code and parser-`expect` false positives, the real production unwraps are:

| Location | Pattern | Verdict |
|---|---|---|
| `fsm-codegen-c/src/stmt.rs` (×~14) | `writeln!(buf, …).unwrap()` into `String` | **Idiomatic but verbose.** `std::fmt::Write` into `String` is infallible. Consider a helper `wln!(buf, …)` macro or local `write_lines!` wrapper to remove the `unwrap()` noise. Not a correctness issue. |
| `fsm-codegen-c/src/emit/history.rs:87` | `let hp_idx = rec.history_pseudo.unwrap();` | **Verify invariant.** This is a real `Option` unwrap on IR data. Likely guarded by a precondition (only called for states known to have a history pseudo), but the invariant should be encoded — either via `expect("history pseudo present because …")` documenting the contract, or by lifting the precondition into the type (e.g., a `HistoryRec` newtype). |
| `fsm-simulator/src/eval/arith.rs:32` | `Value::F64(-v.to_f64().unwrap())` | **Verify invariant.** Likely safe because `Value` only stores finite numbers, but the `to_f64()` contract should be documented inline. Better: `to_f64().unwrap_or(0.0)` is *not* correct here — prefer `expect("Value::Decimal invariant: finite")`. |
| `fsm-cli/src/cmd/generate.rs` (×1) | unverified — single occurrence | Inspect; likely CLI orchestration only. |

**Recommendation:** A focused PR can eliminate ~14 codegen `writeln!.unwrap()` via a single `wln!` macro (3-4 lines), and convert the 2 real Option unwraps to `expect("invariant: …")` documenting the contract. <30-line diff, zero behaviour change, removes the entire "production unwrap" concern.

### 2.5 Test panics in LSP (14 instances) — acceptable

Every LSP `panic!` is inside `#[cfg(test)]` after a `match … { _ => panic!("expected X") }` pattern. Idiomatic. Could be tightened with `assert_matches!`-style helpers, but not a real problem.

### 3.2 Coverage discipline — exceptional

`coverage-floors.toml` implements:
- `measured_*` (honest baseline, recorded for provenance)
- `floor_*` = `floor(measured − 2%)` enforced in CI
- `target_*` = climbed-to goal (line 85 / branch 75; verify stricter at 90/80)
- **Monotonic non-decreasing**: floors can only go up, enforced via `scripts/coverage-gate.py --check-monotonic`
- **Anti-gaming clause**: explicit prohibition on assertion-free line-execution tests

This is the most mature coverage discipline I have seen in a Rust workspace. Keep it as-is.

## 7. My own assessment

**This is one of the best-engineered Rust projects I have audited.** The signals are not subtle:

1. **The project audits itself.** Sixteen formal audit documents in five weeks. Each prior finding leaves a fingerprint in the code (`Audit B P1-A2 (2026-05-15)`, `§11.31 pub-hygiene wave`, `P0-1 / MV5-1 anti-pattern`). The team's discipline around *recording* why a thing is the way it is — directly in Cargo.toml comments and module headers — is what compiler-grade software actually requires.

2. **Architecture is constrained by intent, not by tooling.** The `fsm-verify → fsm-simulator` driver relationship with the explicit "never re-implement transition selection" comment is the single most important architectural choice in a state-machine verifier. They wrote it down. Most projects do not.

3. **The headline smell metrics are misleading because the metric is wrong.** A grep for `unsafe` matches `#![forbid(unsafe_code)]` and historical comments — both *evidence of safety*, not its absence. A grep for `panic!` matches test-only `match _ => panic!(…)` patterns. A grep for `.expect(` matches a parser DSL method `p.expect(TokenKind)`. If you take the surface numbers at face value (388 unwrap, 23 unsafe, 18 panic), you reach the wrong conclusion. **The real production unwrap count in critical paths is under 20, and ~14 of those are infallible `writeln!(String).unwrap()`.**

4. **Where I would push back:** The only real structural debt is `interpreter.rs` at 1899 LOC. Even there, the file is *understandable* — doc-comments point you to each Doc 08 section — but the decomposition is sitting in plain sight (one file per spec section). This is the kind of refactor where the structure was already chosen for you by the spec; you just need to materialize it.

5. **Where I'd push more cautiously:** `import_header.rs` at 1405 LOC for "CLI input convenience" is a genuine smell. C-header parsing has a long tail (typedefs, function pointers, macros, attribute syntax, `const` qualifiers, …) and tends to grow. If you keep this in `fsm-cli`, watch for the moment it crosses 2K — at that point it has stopped being a "convenience" and has become a sub-project hiding in your CLI crate.

6. **The strict-maintainability criteria barely fire on this project.** That review style is calibrated for codebases with creeping ad-hoc complexity. Here, the dominant pattern is: write the spec, encode it explicitly, audit it, document why. The lint policy, dep policy, coverage ratchet, and inline justifications are all working together. The right move is not "clean it up" — it's to keep the discipline, decompose `interpreter.rs`, eliminate the `writeln!.unwrap()` noise, and ship the v1.4 verify epic that's in progress.

**Bottom line:** there is no rescue work here. There is a small, well-scoped maintainability backlog (two P1 items) and a project running at a quality bar most Rust workspaces never reach. I would approve a v1.4 tag against this state without reservation.
