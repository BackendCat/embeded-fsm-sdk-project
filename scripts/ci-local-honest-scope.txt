WHAT THIS GATE DELIBERATELY DID **NOT** RUN LOCALLY — AND WHY (this is
NOT a gap in the gate; it is the CI-first design, OWNER-2 / GT-10):

  • The `on-target` lane (QEMU `mps2-an385` + arm-none-eabi-gcc) and the
    `coverage-rust` lane (cargo-llvm-cov --branch, nightly) are
    CI-RUNNER-ONLY BY DESIGN. arm-none-eabi-gcc / qemu-system-arm /
    cargo-llvm-cov are NOT installed on this disk-tight box and MUST NOT
    be (the no-box-installs constraint). Their `apt-get`/`cargo install`
    lines live in the ci.yml RUNNER jobs and execute in CI, never here.
    THIS GATE MAKES NO CLAIM TO HAVE RUN on-target OR coverage-rust
    LOCALLY.

  • The on-target *LOGIC* is nonetheless LOCALLY SMOKE-PROVEN — not by
    re-running QEMU here, but by W1's HOST generated-C trace differential
    (`codegen_equivalence_smoke`, part of the (a) quad's `cargo test`):
    the generated C is byte-equal to the shipped
    `fsm_simulator::execute_trace` oracle on the host. W2's on-target
    lane runs that SAME instrumented C on a different substrate (QEMU);
    the substrate changes, the oracle does NOT (zero cross-toolchain
    re-implementation by design — the Doc 32 §2 keystone). So the
    on-target *semantics* is locally exercised; only the *emulated-target
    execution* is CI-only.

  • The `act` lane: `act` is ABSENT on this box but installable (Docker
    IS present, so `act` runs once installed). It pulls multi-GB runner
    images and the box is disk-tight (GT-10), so even when present `act`
    covers ONLY the Linux `build`/`sca` lanes — never the heavy matrix.
    If `act` is absent this gate reports lane (d) as
    `SKIPPED — pending act install` and CONTINUES (an honest skip, the
    `gcc_compile.rs` skip-notice precedent) — it NEVER silently passes
    that lane, and it does NOT install `act` to "make it work".
